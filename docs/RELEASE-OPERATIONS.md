## Trust boundary

The shared catalog and each product manifest use a deliberately limited single-role RSA-PSS/SHA256 envelope: exact UTF-8 payload bytes in Base64 plus signature, with build-pinned RSA SPKI public keys of at least3072 bits. Signed payloads bind product/channel/platform/version, monotonic sequence, expiry, full source commit and artifact hashes/lengths. Genesis schema1 remains exactly unchanged, including saveSchema. Hub schema1 additionally binds minimumHubVersion, minimumWindowsBuild and installer.publisherThumbprint. Catalog is separate from the existing Genesis locator; catalog alone never authenticates executable bytes.

Online catalog/install metadata rejects expiry and sequence rollback. Approved catalog availability/provenance/download fields must match the independent product manifest. Hub updates require a strictly new sequence/version. Offline managed Genesis Play accepts stored expiry but verifies the stored signature and every declared file again. Rollback explicitly preserves the highest sequence and requires identical saveSchema; it backs up saves without restoring or deleting them. A local administrator/user capable of replacing application files or deleting local sequence state is outside this limited anti-replay threat model.

This is **not TUF**: no threshold roles, delegated metadata, trusted root document, automatic root rotation, signed revocation distribution or recovery ceremony is implemented. Key replacement requires an independently reviewed new Hub installer with new embedded trust. Protect signing keys offline/HSM, review fingerprints out of band and obtain independent security review before public distribution. Metadata-only renewal with identical version/packages and increased sequence must use the separately reviewed distribution renewal tooling; the legacy Hub ReleaseTool still requires increasing product versions. Renew before expiry; installed offline games remain playable after metadata expiry.

## Known Windows publisher and self-update

HUB_PUBLISHER_SHA256 is the independently reviewed uppercase64hex SHA256 digest of the signing certificate's DER bytes, not its usual SHA1 thumbprint and never a remote manifest-provided trust pin. Bootstrapper uses single-file publishing with native runtime libraries included for self-extraction; Windows smoke copies only the EXE and invalidates SDK bindings to prove its own fail-closed handler starts. Both Hub and self-contained bootstrapper embed the same Hub metadata key/publisher pin. Downloaded manifest.publisherThumbprint must equal that known pin. Windows WinVerifyTrust checks Authenticode chain/signature/revocation policy, then the actual signer certificate SHA256 must match. Missing pin/key, unavailable/untrusted Windows verification or mismatch stops the update. No production Authenticode signing service is configured or demonstrated by this branch; synthetic unsigned fixtures are rejected.

The Hub downloads to a GUID stage, checks signed size/hash/publisher and asks explicitly before handoff. It copies the standalone bootstrapper into that stage so the installed bootstrapper is not running during replacement. The copied bootstrapper accepts only parent PID/start-time arguments, never public keys, publishers, paths or arbitrary commands. Stage/target ancestors reject reparse links. It validates parent process start time and executable against the registered per-user installed Hub path, retains that process handle, acknowledges readiness, and waits up to five minutes for exit without killing Hub. A canceled/failed handoff writes a stage cancel marker checked while waiting and before proceeding, so later unrelated Hub exit cannot trigger installation. If the marker cannot be written (full/read-only stage), Hub terminates and waits for its own bootstrap child before returning; it never kills the parent Hub or rediscovers a process by PID. It refuses another running Hub at that installed path, independently reverifies all trust and installer bytes, and holds the installer read-only during verification/launch. It opens the interactive installer wizard; it does not silently elevate or terminate games. Success requires installer exit0 **and** installed ProductVersion matching the signed version before persisting sequence. Errors display a separate bootstrapper message and attempt a fixed local bootstrap-last-error.json diagnostic; diagnostic failure never executes an installer. Staging or launch is not a successful update claim.

The NSIS installer preserves user scope and registered installation location. This bootstrapper is a verified handoff, not transactional binary rollback: NSIS interruption or power loss can leave an incomplete Hub install; use the same independently trusted installer to repair it. High-DPI, publisher-chain revocation networking, installer-cancel/repair and real production-signed happy-path acceptance require Windows testing. No trust bypass is provided.

Maintained frameworks such as Velopack should be evaluated for production Hub self-update packaging/recovery. Migrating the current NSIS installation and separate Genesis component/save activation to a new framework would require a reviewed format and trust migration; bolting one in during this milestone would not establish its deployment guarantees. The constrained bootstrapper retains the reviewed existing installer, while full update durability/root trust remains explicitly limited. Do not claim a maintained framework or TUF integration is already present.

## Files, saves and storage

Managed game root is default %LOCALAPPDATA%/EvidenceNeuterHub/Genesis or a Settings-selected dedicated EvidenceNeuterHub/Genesis child for new installations. Existing managed versions cannot be silently relocated. GUID stage, cache, versions, active.json and save-backups remain under that root. Package downloads restart after cancel; partials are removed. Verified matching installed/imported files and package cache are reused per component, while copies still need staging disk space. Real byte/speed progress is measured from streams.

Activation flushes/replaces the active/previous pointer after complete file verification and whole-tree %APPDATA%/EvidenceGenesis backup. Failed/canceled/interrupted staging preserves the previous pointer; abandoned GUID stages are recovered under the lock. Filesystem/power-loss durability is not hardware fault-tested. Genesis0.4 profiles use compatibility epoch4 (internal statev4); legacy statev2/v3 imports are read-only. The separately reviewed managed Genesis0.3.0(epoch1)→0.4.0(epoch4) forward transition is permitted with minimumHub0.3 and whole-tree backup. It changes binaries only; the player explicitly selects Import legacy workshop (keep original) in the new game to create a separate v4 profile. Continue does not automatically import. All other cross-epoch transitions and epoch4→1 rollback are blocked. No automatic save restore/rewrite occurs.

Generated cache/staging cleanup holds the same install lock, rejects reparse links and malicious state, and preserves active/previous versions, save-backups and original imported folders. Updates/rollback/cleanup are blocked while EvidenceGenesis runs. External direct launches cannot be fully synchronized, though managed version files are never replaced in place. Corrupt settings are preserved; writes are disabled until repaired.
